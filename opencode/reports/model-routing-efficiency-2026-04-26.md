# Model Routing Efficiency Report

Date: 2026-04-26

This report captures a small OpenCode routing test focused on whether delegated work is handled by cheaper or standard workers instead of the heavy worker.

Data source: OpenCode session exports and the local OpenCode SQLite database, grouping assistant messages by worker agent and recorded token metadata.

## Summary

Three read-only tests were executed against this repository:

1. `worker-lite` checked whether the root README contains cost metrics.
2. `worker-standard` reviewed the two README files for publication improvements.
3. `worker-standard` reviewed the planner-to-orchestrator handoff.

Observed result:

- Worker sessions: 3
- Worker calls: 7
- `worker-lite` calls: 3
- `worker-standard` calls: 4
- `worker-heavy` calls: 0
- Input tokens handled by workers: 15.7K
- Output tokens generated by workers: 686
- Cache read tokens for workers: 28.7K

The notable result is that all delegated work was handled by `worker-lite` or `worker-standard`. No `worker-heavy` call was needed.

## Cost Interpretation

OpenCode reported `$0.0000` for direct OpenAI OAuth usage, so this run should not be treated as a dollar-spend measurement.

The useful efficiency signal is routing behavior:

- 15.7K worker input tokens and 686 worker output tokens were handled without using the heavy model.
- If those same calls had been forced through `worker-heavy`, the token volume would have been billed or accounted at the heavy model tier.
- Since heavy models normally have a higher per-token price than mini or standard models, routing these tasks away from `worker-heavy` is the expected source of savings.

Savings formula for a priced API run:

```text
estimated_savings =
  cost_if_all_worker_tokens_used_heavy_model
  - actual_routed_worker_cost
```

Where:

```text
cost_if_all_worker_tokens_used_heavy_model =
  worker_input_tokens * heavy_input_price
  + worker_output_tokens * heavy_output_price
```

And:

```text
actual_routed_worker_cost =
  lite_input_tokens * lite_input_price
  + lite_output_tokens * lite_output_price
  + standard_input_tokens * standard_input_price
  + standard_output_tokens * standard_output_price
```

## Notes

- This is a small pilot, not a statistically significant benchmark.
- The test was read-only, so it measured routing behavior rather than implementation quality.
- A `worker-heavy` test was attempted, but the route is configured with `ask`, so non-interactive execution did not proceed automatically. This is desirable from a safety perspective: heavy/high-risk work requires explicit approval.
- Future reports should include current provider pricing at the time of the run if dollar savings are published.
